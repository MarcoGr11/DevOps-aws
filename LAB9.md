# Лаба 9 — балансування навантаження і доступність

Той самий API бронювання коворкінгу з лаби 8 запущено в трьох контейнерах, перед ними
стоїть nginx як балансувальник. Дані лежать у DynamoDB у LocalStack, спільній для всіх
екземплярів. Досліджено, як система поводиться, коли один екземпляр зупиняється і знову
запускається, а також чим вона відрізняється від варіанту з одним екземпляром без
балансувальника.

## Архітектура

```
               curl / load.sh / failover-demo.sh / compare.sh
                                 │ HTTP 127.0.0.1:8080
                ┌────────────────▼─────────────────┐
                │ nginx 1.28 (upstream, round-robin,│
                │ max_fails=2 fail_timeout=5s)      │
                └───┬──────────────┬──────────────┬─┘
        172.30.9.11 │  172.30.9.12 │  172.30.9.13 │   :8000
             ┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼─────┐
             │ app1        │ │ app2       │ │ app3       │  один образ bookings-app:lab9,
             │ instance-1  │ │ instance-2 │ │ instance-3 │  різний INSTANCE_ID
             └──────┬──────┘ └─────┬──────┘ └─────┬──────┘
                    └──────────────┼──────────────┘ boto3, AWS_ENDPOINT_URL
                          ┌────────▼────────┐
                          │ LocalStack 4.9.2│  DynamoDB, таблиця bookings
                          └─────────────────┘  (створює init-table, одноразово)

   app-single (профіль nolb) ── 127.0.0.1:8081 ── той самий образ, без балансувальника
```

Кожна відповідь має заголовок `X-Instance-Id: instance-N`. `GET /health` повертає
`{"status":"ok","instance":"instance-N"}`, тому з відповіді видно, хто її обробив.

## Що і чому так зроблено

| Рішення | Чому |
|---|---|
| `app/server.py` — тонкий адаптер на stdlib `http.server` | бізнес-логіку не переписано: HTTP-запит перетворюється на подію API Gateway proxy (`httpMethod`, `resource`, `pathParameters`, `headers`, `body`) і передається в `lambda_handler` з лаби 8. Зовнішні залежності — лише boto3 |
| `handler.py` не змінено | `health()` уже читає `INSTANCE_ID`; заголовок `X-Instance-Id` додає адаптер. Тести лаби 8 не зачеплено |
| Dockerfile збирається з кореня репо | `COPY lambda/handler.py` бере той самий файл, що й Lambda, без копії коду. `.dockerignore` пропускає в контекст лише 4 потрібні файли |
| Окремий `docker-compose.lab9.yml` з `name: devops-lab9` | `docker-compose.yml` лаби 8 не змінено; LocalStack лаби 9 не публікує порт 4566, тож обидва стеки можуть працювати одночасно |
| `init-table` з того самого образу (boto3) | ідемпотентне створення таблиці без додаткового образу aws-cli; `app1..3` стартують лише після його успішного завершення |
| Фіксовані IP бекендів + `extra_hosts` у nginx | див. «Чому не DNS Docker» нижче |

### Чому не DNS Docker (`resolve`)

Спершу upstream використовував `server app2:8000 resolve` і `resolver 127.0.0.11 valid=5s`.
Під час `compare.sh` один запит із 30 отримав **502**. У журналі nginx: спроба до app2 —
`504` (таймаут з'єднання 1 с), а за цю секунду nginx перерезолвив імена, конфігурація
upstream змінилася, і повторна спроба завершилася `no live upstreams`. Отже, це гонка між
повтором запиту і оновленням DNS.

Тому імена `app1..app3` задано статично в `/etc/hosts` контейнера nginx (`extra_hosts`) з
фіксованими IP (`ipv4_address`, динамічні адреси мережі — з діапазону `.128/25`). Тепер
вибір сервера визначає лише пасивна перевірка `max_fails/fail_timeout`. Після цієї зміни
три прогони `compare.sh` і 300 запитів `GET /bookings` при зупиненому app2 пройшли без
жодної помилки.

## nginx.conf по директивах

| Директива | Значення | Навіщо |
|---|---|---|
| `upstream bookings_backend` | 3 сервери `appN:8000` | пул екземплярів; алгоритм за замовчуванням — round-robin |
| `max_fails=2 fail_timeout=5s` | на кожному сервері | 2 невдалі спроби за 5 с → сервер виключено на 5 с, потім nginx знову пробує його реальним запитом (пасивна перевірка) |
| `proxy_pass http://bookings_backend` | `location /` | усі запити API йдуть у пул |
| `proxy_set_header Host / X-Real-IP / X-Forwarded-For` | | бекенд бачить оригінальний Host і IP клієнта |
| `proxy_connect_timeout 1s` | | мертвий екземпляр «коштує» не більше 1 с |
| `proxy_send_timeout 5s`, `proxy_read_timeout 5s` | | обмеження на передачу запиту й очікування відповіді |
| `proxy_next_upstream error timeout http_502 http_503 http_504` | | за таких помилок запит повторюється на наступному сервері. POST повторюється, лише якщо ще не був відправлений бекенду (помилка з'єднання), тож дублікатів записів не буде |
| `proxy_next_upstream_tries 3`, `proxy_next_upstream_timeout 5s` | | не більше 3 спроб і 5 с на запит |
| `location = /nginx-health` | `return 200` | живість самого балансувальника (healthcheck контейнера nginx) |
| `log_format lb` | `$upstream_addr`, `$upstream_status`, `X-Instance-Id`, `$request_time` | у `docker compose logs nginx` видно спроби, повтори і час |
| `X-Instance-Id` | — | nginx передає заголовки бекенда клієнту за замовчуванням |

Healthcheck є в усіх контейнерах: `app*` — `HEALTHCHECK` у Dockerfile (`/health` через
urllib), `nginx` — `wget /nginx-health`, `localstack` — `/_localstack/health`. nginx
стартує через `depends_on: condition: service_healthy` лише після трьох здорових бекендів.

## Послідовність запуску

```bash
# LocalStack + init таблиці + app1..app3 + nginx, чекати healthy
docker compose -f docker-compose.lab9.yml up -d --build --wait     # або: make lab9-up
docker compose -f docker-compose.lab9.yml ps

# запити через балансувальник
curl -si localhost:8080/health
scripts/lab9/load.sh 30                 # розподіл 30 запитів + 3 POST у спільну БД
scripts/lab9/failover-demo.sh           # stop app2 -> запити -> start app2 -> запити
scripts/lab9/compare.sh                 # з балансуванням і без (app-single на :8081)

# прибирання
docker compose -f docker-compose.lab9.yml --profile nolb down       # або: make lab9-down
```

Перший `up --build` триває близько 45 с (збірка образу і старт LocalStack). Повторні
запуски швидші. Тести: `make test` (pytest + ruff, разом з тестами лаби 8).

## Сценарій failover (`failover-demo.sh` або вручну, як на знімках звіту)

1. 30 запитів `GET /health` — розподіл 10/10/10.
2. `docker compose stop app2` — `app2: Exited (0)`.
3. 30 запитів — усі 200, лише app1 і app3. Запит, який nginx першим відправляє на зупинений
   app2, чекає `proxy_connect_timeout` (≈1,0 с) і повторюється на наступному сервері, тому
   розподіл може бути не рівно 15/15. Після 2 таких спроб app2 виключено на 5 с, тож
   повільних запитів лише кілька.
4. `docker compose start app2` → healthy → пауза до `fail_timeout` (5 с) → 30 запитів —
   знову 10/10/10.

Виміряно під час зйомки звіту (`load.sh 30` на кожному етапі):

| етап | 200 | помилки | app1 | app2 | app3 | сер. час, с | макс. час, с |
|---|---|---|---|---|---|---|---|
| усі працюють | 30 | 0 | 10 | 10 | 10 | 0,002 | 0,007 |
| app2 зупинено | 30 | 0 | 14 | 0 | 16 | 0,070 | 1,025 |
| app2 відновлено | 30 | 0 | 10 | 10 | 10 | 0,004 | 0,017 |

Окремий прогін `failover-demo.sh` дав 30/30, 15/0/15 і 2 запити по ≈1,01 с. Ще 300 запитів
`GET /bookings` (зі зверненням до DynamoDB) при зупиненому app2 — 300/300 успішних,
150/150 між app1 і app3, максимальний час 1,016 с.

## З балансуванням і без (`compare.sh`)

| сценарій | всього | 200 | помилки | успіх, % | сер. час, с |
|---|---|---|---|---|---|
| з балансуванням, працюють 3 з 3 | 30 | 30 | 0 | 100 | 0,002 |
| без балансування, працює 1 з 1 | 30 | 30 | 0 | 100 | 0,002 |
| з балансуванням, app2 зупинено (2 з 3) | 30 | 30 | 0 | 100 | 0,070 |
| без балансування, екземпляр зупинено (0 з 1) | 30 | 0 | 30 | 0 | 0,000 (connection refused) |

Коли всі екземпляри здорові, різниці в часі відповіді на `/health` немає: накладні витрати
nginx на цьому навантаженні не помітні. Різниця — у доступності: з балансувальником відмова
одного екземпляра не дала жодної помилки, без нього — 100% помилок. Ціна — кілька
запитів по ≈1 с у момент виявлення відмови.

## Обмеження

- **Пасивні health-check.** Open-source nginx дізнається про падіння екземпляра лише з
  невдалого реального запиту, тому перший запит до мертвого екземпляра повільніший
  (≈1 с, `proxy_connect_timeout`). Кожні 5 с (`fail_timeout`) nginx знову пробує виключений
  сервер реальним запитом. Активні перевірки (`health_check`) є лише в NGINX Plus або в
  HAProxy/Traefik/AWS ALB.
- **Round-robin не враховує навантаження** і час відповіді: повільний екземпляр отримує
  стільки ж запитів, скільки й швидкий (альтернативи — `least_conn`, `random two`).
- **Єдині точки відмови.** nginx — один контейнер. DynamoDB у LocalStack — одна на всіх. Якщо
  впаде будь-який із них, відмовить усе.
- **Статичні IP** — плата за детермінований failover. Для динамічного масштабування
  (`--scale`) потрібен DNS-резолвінг або service discovery.
- Вимірювання — на одному ноутбуці (Docker Desktop, macOS), невелике навантаження з одного
  клієнта. Абсолютні числа часу не переносяться на реальне середовище.
