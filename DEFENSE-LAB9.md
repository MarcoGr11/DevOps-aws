# Шпаргалка для захисту лаби 9

## Простими словами

- **Балансувальник навантаження** — «диспетчер» перед кількома копіями застосунку. Клієнт
  знає одну адресу (`localhost:8080`), а балансувальник вирішує, якій копії віддати запит.
- **Upstream** — у nginx це іменована група серверів (`bookings_backend` = app1, app2, app3),
  між якими розподіляються запити.
- **Round-robin** — по черзі: 1, 2, 3, 1, 2, 3… Простий і рівномірний, але не дивиться, хто
  зараз зайнятий.
- **Health check** — перевірка, чи живий екземпляр.
  - *Пасивний* (open-source nginx): балансувальник помічає збій лише на реальному запиті
    (`max_fails=2` невдачі за `fail_timeout=5s` → сервер виключено на 5 с).
  - *Активний* (NGINX Plus, HAProxy, AWS ALB): балансувальник сам періодично опитує
    `/health` і виключає хворий екземпляр ще до того, як на нього прийде запит клієнта.
- **Failover** — автоматичне перемикання на живі екземпляри, коли один відмовив. Тут: запит
  до мертвого app2 повторюється на app1/app3 (`proxy_next_upstream`), клієнт отримує 200.
- **Чому 3 екземпляри** — при відмові одного лишається два, тобто резерв усе ще є;
  щонайменше 3 потрібно, щоб показати рівномірний розподіл і відмову без втрати резерву.
- **Горизонтальне масштабування** — більше копій (app1..app3). **Вертикальне** — більше
  CPU/RAM одній копії. Горизонтальне дає ще й відмовостійкість, вертикальне — ні.
- **Single point of failure (SPOF)** — компонент, відмова якого кладе всю систему. Тут це
  nginx і DynamoDB (LocalStack): вони в одному екземплярі.

## Жива демонстрація (5–7 хв)

```bash
cd ~/PycharmProjects/DevOps-aws
C="docker compose -f docker-compose.lab9.yml"

# 1. Підняти стек (≈45 с з нуля) — "один образ, три контейнери з різним INSTANCE_ID"
$C up -d --build --wait
$C ps                                   # app1..3 healthy, nginx healthy, init-table exited (0)

# 2. Балансування видно в заголовку і тілі — "по черзі 1-2-3"
for i in 1 2 3 4 5 6; do curl -s localhost:8080/health; echo; done

# 3. Розподіл і спільна БД — "10/10/10; запис, створений одним, читає інший"
scripts/lab9/load.sh 30

# 4. Failover — "зупиняю app2: усі 200, лише кілька запитів по ~1 с"
scripts/lab9/failover-demo.sh

# 5. Порівняння — "з балансувальником 100%, без — 0%"
scripts/lab9/compare.sh

# 6. Журнал nginx — "видно повтор: upstream_status=504, 200"
$C logs nginx | grep ', ' | tail -3

# 7. Тести
make test
```

Що говорити: адаптер `app/server.py` перетворює HTTP-запит на подію API Gateway і викликає
той самий `lambda_handler`, що й у лабі 8; nginx розподіляє запити round-robin; при відмові
спрацьовують `proxy_next_upstream` (повтор) і `max_fails/fail_timeout` (виключення на 5 с).

## Ймовірні питання

1. **Чому nginx, а не AWS ELB/ALB?**
   ALB не входить у безкоштовну версію LocalStack і є лише в AWS, а nginx працює локально в
   Docker і дає ті самі концепції (пул, алгоритм, health-check, retry). У реальному AWS на
   цьому місці стояв би ALB з target group.

2. **Що буде, якщо впаде nginx?**
   Система стане недоступною: nginx — SPOF. Рішення — два балансувальники з плаваючою IP
   (keepalived/VRRP) або керований балансувальник (ALB), який AWS сам робить відмовостійким.

3. **Чому дані спільні, а не в кожному екземплярі?**
   Інакше запис, створений на app1, не знайшовся б на app2, бо наступний запит іде на інший
   екземпляр. Екземпляри застосунку без стану (stateless), стан — у DynamoDB. Це й дозволяє
   вільно додавати чи прибирати копії.

4. **Що таке sticky sessions?**
   Прив'язка клієнта до одного екземпляра (cookie або `ip_hash`). Потрібна, коли стан
   зберігається в пам'яті екземпляра. Мінус: при відмові екземпляра сесія губиться, а
   навантаження розподіляється нерівномірно. Тут не потрібна, бо застосунок stateless.

5. **Чим пасивний health-check гірший за активний?**
   Пасивний дізнається про відмову з реального запиту: кілька клієнтів отримують затримку
   (тут ≈1 с). Крім того, «напівживий» екземпляр, що відповідає 200 на з'єднання, але
   зламаний усередині, не виявляється. Активний опитує `/health` у фоні й виключає екземпляр
   заздалегідь.

6. **Чому після зупинки app2 деякі запити тривали ~1 с, а не впали?**
   nginx пробує з'єднатися з app2, чекає `proxy_connect_timeout 1s`, далі
   `proxy_next_upstream` повторює запит на app1/app3. Після 2 невдач (`max_fails=2`) app2
   виключено на 5 с, тому повільних запитів лише кілька.

7. **Чи не продублює повтор POST-запит?**
   Ні. За замовчуванням nginx не повторює неідемпотентні запити (POST), якщо вони вже були
   надіслані бекенду. Повтор відбувається лише при помилці з'єднання, тобто коли бекенд
   запиту не отримав.

8. **Чому статичні IP, а не DNS Docker?**
   Ім'я зупиненого контейнера зникає з DNS Docker. Із `resolve` nginx перечитував імена під
   час повтору, і я спіймав 1 помилку 502 на 30 запитів (`no live upstreams`). Зі статичними
   IP ім'я завжди резолвиться, а доступність визначає лише пасивна перевірка — 0 помилок у
   трьох прогонах.

9. **Як додати четвертий екземпляр?**
   Сервіс `app4` у compose (той самий образ, `INSTANCE_ID=instance-4`, IP `.14`), рядок
   `server app4:8000 ...` в upstream і `extra_hosts`, потім `up -d`. Для динамічного
   масштабування — service discovery або DNS з `resolve`.

10. **Як nginx розуміє, що app2 повернувся?**
    Через `fail_timeout=5s` nginx знову відправляє на app2 реальний запит. Якщо той успішний,
    app2 повертається в ротацію. Тому скрипт після `start app2` чекає healthy і ще 6 с, після
    чого розподіл знову 10/10/10.
